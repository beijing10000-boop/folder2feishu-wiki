# Folder2Feishu Wiki 2.0 性能与稳定性改造报告

日期：2026-08-03  
基线：`2451c1b`  
备份标签：`backup-pre-perf-stability-20260803`  
实施分支：`perf/stability-v1`

## 1. 新程序边界

2.0 按全新程序交付，不导入旧版数据库、配置或凭据。安装目录改为
`%LOCALAPPDATA%\Programs\Folder2FeishuWikiNext`，运行数据改为
`%LOCALAPPDATA%\Folder2FeishuWikiNext`。旧版本可独立保留用于回退。

业务规则未改变：本地目录只读、按原层级进入飞书知识库、云盘仅作中转、先确认计划再写入、
不删除本地或飞书内容、0 字节文件记录后跳过。

## 2. 架构与迁移链路

```text
浏览器
  -> 快速 HTTP 命令（创建 durable task_id 后立即返回）
  -> SQLite 任务/台账（WAL、单写者项目锁、心跳、断点）
  -> 有界后台执行器（扫描 / 计划 / 迁移 / 对账）
  -> 有界 HTTP 连接池（超时、有限重试、指数退避）
  -> 飞书 Drive 中转 -> Wiki 迁入 -> 远端回读校验

浏览器 <- 任务状态增量查询 / 审计增量查询 / 分页目录树
```

迁移阶段固定为：参数检查、网络检查、权限检查、源数据扫描、目标检查、预处理、
数据迁移、数据校验、失败项重试、结果汇总。每个后台任务持久化任务 ID、阶段、状态、
总量、完成/失败/跳过数、字节进度、当前对象、开始时间、预计剩余时间、心跳及最后消息。

## 3. 已确认问题与处理

| 优先级 | 位置 | 代码或实测证据 | 原因与影响 | 处理 | 风险 |
|---|---|---|---|---|---|
| P0 | 计划接口 | 基线 `POST /plan` 内直接调用 `planner.build` | 数万动作生成长期占用 HTTP 请求，按钮无反馈且容易被重复提交 | 改为持久化后台任务，立即返回 task_id，同项目去重 | 低 |
| P0 | 远端对账 | 基线 `POST /reconcile` 内同步遍历远端 | 网络波动会占住 Web 工作线程，前端误判“卡死” | 后台化并提供心跳、取消和恢复 | 低 |
| P0 | 服务重启 | 运行状态缺少遗留任务收口 | 进程退出后任务可能永久显示处理中 | 启动时把无主 QUEUED/RUNNING 标为 INTERRUPTED，可从台账恢复 | 中 |
| P0 | 网络请求 | 基线采用 120 秒读取超时、无显式连接池上限，重试等待不可中断 | 慢连接和并发请求可能长时间占用 Socket/线程；这是应用层连接堆积风险，不是已证实的 Windows 网卡故障 | connect/read/write/pool 分离超时，连接池 8/4，有限指数退避，暂停/取消可中断等待 | 中 |
| P0 | 异常处理 | 后台执行器捕获异常但未输出完整堆栈 | 无法按 task_id 定位失败代码 | JSON 结构化日志，后台异常写完整堆栈并绑定 task_id/stage | 低 |
| P1 | 扫描写库 | 每 500 行编译一个超长多值 UPSERT，且每 100 项更新任务记录 | 大量 SQL 编译、事务和磁盘同步；35k 扫描实测约 350.8 秒 | 改为可复用语句 executemany、1000 行批次、进度按时间/1000 项持久化 | 低 |
| P1 | 文件哈希 | 4 个 worker、最多 8 个排队任务 | Windows 小文件 I/O 流水线过浅 | 8 个受控 worker、最多 64 个待处理任务，仍保持内存有界 | 中（慢盘可能需降并发） |
| P1 | 项目摘要 | 基线 `inventory_summary` 加载全部 Inventory ORM 后在 Python 聚合 | 5 万行页面打开慢且占内存 | SQL 聚合计数/总字节/问题数，仅读取摘要 | 低 |
| P1 | 目录树 | 基线一次加载并序列化全部目录和文件 | 大数据首屏慢、响应体大、React 渲染阻塞 | 目录分页、按父目录懒加载，前端展开时读取 | 中 |
| P1 | 计划页面 | 基线加载全部动作和全部 Inventory 建映射 | 5 万动作造成接口、JSON 和浏览器内存压力 | 后端聚合计数，只返回每类有界预览；执行端每批 200 条 | 中 |
| P1 | 执行器 | 基线迁移前一次加载全部计划动作及 inventory | 大任务内存峰值高，无法细粒度续传 | 每批独立读取、落库和推进；token/task/wiki token 即时持久化 | 中 |
| P1 | 前端轮询 | 旧轮询无页面可见性降频、请求重叠保护不足 | 后端慢时可能堆积重复状态请求 | 单飞轮询，前台 2 秒、后台 5 秒，离页停止；请求有 15/20 秒超时 | 低 |
| P2 | 日志列表 | 每次获取整段审计记录 | 运行越久响应越慢 | 使用 after_id + limit 增量读取 | 低 |
| P2 | 可观测性 | 无统一接口时延、连接与资源指标 | 只能凭界面判断“卡死” | `/api/v2/metrics` 输出 API P95/P99、HTTP 错误/超时/重试、CPU/内存/线程/连接/I/O | 低 |

## 4. 性能结果

测试环境为当前 Windows 开发机、同一份 35,000 个 1 字节文件和 5,051 个目录：

| 指标 | 优化前 | 优化后 | 结果 |
|---|---:|---:|---:|
| 首次扫描耗时 | 350.797 秒 | 40.282 秒 | 快约 8.7 倍，降低 88.5% |
| 完整规模验收 | 未通过 `<180 秒` | 通过 | 35,000 文件、5,051 目录完整 |
| 后端自动测试 | — | 123 通过、1 个规模测试默认跳过 | 通过 |
| 前端自动测试 | — | 10 通过 | 通过 |
| 前端生产构建 | — | 1,580 模块，1.84 秒 | 通过 |
| 静态检查 | — | Ruff、mypy 均零错误 | 通过 |
| 同层目录迁移模拟 | 3.556 秒 | 1.263 秒 | 快约 2.82 倍 |
| 目录加文件迁移模拟 | 13.188 秒 | 4.008 秒 | 快约 3.29 倍 |

完整规模 pytest 的 152 秒墙钟时间还包含现场创建 40,051 个测试对象；断言计时只覆盖扫描，
并已通过 180 秒要求。真实 307 GB 数据的总时间仍主要由磁盘读取、文件下载状态和上行带宽决定。

## 5. 数据库变更

- schema 版本提升到 2。
- `job_runs` 增加阶段、当前对象、消息、字节进度、重试数、暂停/取消、心跳字段。
- 新增任务状态/心跳、项目/计划/状态等查询索引。
- SQLite 继续使用 WAL、`busy_timeout`、短事务和项目级锁。
- 大批 inventory 与 plan 写入改为 executemany；迁移执行每批 200 项。

本次按新程序交付，不对旧数据库执行原地升级。回滚不需要数据库降级。

## 6. 用户可见行为

- 点击盘点、生成计划、开始迁移、远端对账后立即显示“已受理”和 task_id。
- 页面展示阶段、百分比、当前文件、完成/失败/跳过数、耗时、ETA、最后心跳和实时审计。
- 支持安全暂停、继续、停止、重试失败项和查看详细错误。
- 刷新或关闭浏览器后，通过项目任务列表恢复最近任务。
- 重复点击返回同一个活动任务，不重复创建迁移。
- 服务重启后遗留运行标记为“已中断”，不会永久处于“处理中”。
- 单个文件失败落库后继续后续项；临时网络错误有限重试，未知写入结果先远端对账。

## 7. 日志与指标

日志路径：`%LOCALAPPDATA%\Folder2FeishuWikiNext\logs\folder2feishu.log`。
每行是 JSON，包含 server_time、level、logger、message、request_id、task_id、stage；
可选包含 user_id、batch、processed、path、duration_ms、retry_count、error_type 和 exception。
凭据、Bearer token、refresh token 和 client secret 会脱敏。

`GET /api/v2/metrics` 提供 API 平均/P95/P99、飞书 HTTP 活跃数/错误/超时/重试、
进程 CPU、内存、线程、打开文件、网络连接与磁盘读写。任务运行数和等待数由任务状态统计返回。

## 7.1 迁移流水线补充优化

- 同层且互不依赖的目录由最多 4 个工作线程并行创建；完成当前深度后才进入下一层，保证父节点先于子节点落库。
- 独立文件以有界并发执行上传、迁入、轮询和校验；最多只预取工作线程数两倍的动作，避免把全量计划装入内存。
- 每个远端 token 仍立即持久化；普通进度约每秒批量刷新一次，降低 SQLite 高频写入。
- Wiki 创建通道默认按 100 次/分钟限流。并发只用于覆盖远端等待时间，不突破飞书接口限制。
- 上表迁移结果使用确定性模拟远端延迟，用于验证调度优化；真实环境速度需以飞书响应、文件大小和租户限流为准。

## 8. 部署

1. 关闭旧版 Folder2Feishu，确认 8000 端口空闲。
2. 解压 2.0 发布 ZIP。
3. 双击 `Install.cmd`，或运行 `deploy\Install-Folder2Feishu.ps1`。
4. 使用新桌面快捷方式 `Folder2Feishu Wiki Next`。
5. 在全新的配置页重新填写 App ID、App Secret、本地根目录和目标 Wiki，并重新 OAuth。
6. 先用 3–10 个代表文件完成试迁、重启恢复、复跑和哈希抽样，再迁移全量。

## 9. 回滚

代码回滚点为 Git 标签 `backup-pre-perf-stability-20260803`。部署回滚时：

1. 停止新版服务。
2. 重新启动旧版安装目录中的启动脚本。
3. 新版运行数据位于独立 `Folder2FeishuWikiNext`，不会覆盖旧版台账。
4. 若仅回滚新版代码，使用上一发布 ZIP 覆盖新版安装目录；保留新版 runtime 目录用于审计。

不要自动删除已在飞书创建的试点节点；按审计导出人工核对。

## 10. 未解决和真实环境待验收项

- 当前开发环境没有用户的有效飞书 OAuth 和 307 GB 源目录，因此没有执行真实飞书写入或抽样下载哈希。
- 需要在部署电脑完成小批试迁、断网恢复、服务重启恢复、重复运行、修改/移动/改名和远端回读。
- `/api/v2/metrics` 是单进程滚动指标，不是长期监控系统；如需长期趋势可后续接 Prometheus。
- 扫描并发默认 8；若来源为机械盘或网络盘，应根据实测将其调低，不能盲目增加线程。
